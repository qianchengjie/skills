# 切片开发 · decisions.md 文件

## 职责

`decisions.md` 保存会改变整体拆分、task immutable contract、依赖、公共行为或用户授权边界的真实分叉。plan 的 `关联项` 只保存 D 的 ID 和状态摘要。

文件落点、执行 allowlist、测试位置、验证命令、规则适用性和内部实现方案默认由 `deliver-task` 在授权边界内判断，不创建 D。只有它们反过来要求改变目标、验收、约束、非目标、禁止范围、调用策略或不可逆外部动作时才回到 D。

## ID 与模板

D* 使用数字路径，例如 `D1`、`D27`、`D27.1`。标题必须以 ID 开头：

```markdown
### D27：是否保持旧接口兼容

- 状态：open
- 关联：S2 / S3
- 问题：<一次只问一个具体问题>
- 推荐：<有依据的推荐答案>
- 证据：<短证据或 plan 根目录 A*>
```

确认后改为：

```markdown
### D27：是否保持旧接口兼容

- 状态：decided
- 关联：S2 / S3
- 结论：<会约束后续 task contract 的稳定口径>
- 证据：<短证据或 plan 根目录 A*>
```

## 状态

- `open`：仍等待用户 / upstream 拍板；必须有 `问题 / 推荐`，关联 slice 必须 `blocked`。
- `decided`：已形成唯一口径；必须有 `结论`。

每个 D 都必须有 `状态 / 关联`。`证据` 可引用 plan 根目录 A*；不要用 plan D 直接引用 task-owned General 或验收正文，如确需说明计划影响，先在 plan A* 记录影响与 task evidence ref。

## skipped 依据

切片写 `状态：skipped` 时，`跳过依据` 必须是一个 `decided` D，并在本片 `关联项` 中同样标为 `decided`。D 的 `关联` 应包含该片，`结论` 说明稳定的不做口径。

validator 检查 D 存在和明确状态，不判断结论或证据是否足以支持跳过。

## 维护规则

- 发现分叉先写 D，再关联 slice；不在会话里保留唯一真值。
- 用户确认后写稳定结论，不记录问答流水。
- 一个 D 只表达一个选择；相关但不同的产品 / 契约问题分别记录。
- 会影响多个 task 的决定提炼进顶层 `全局约束`；只影响一片的决定留在该片合同与 D。
- 下游 `needs-upstream` 只有在 immutable contract 或用户判断确实变化时才形成 / 更新 D；执行边界调整不建 D。
