# 项目知识库维护

把开发与探索过程中形成的有效知识整理到项目的正式维护位置，供后续理解、维护和复用。以已有材料的实际职责确定维护位置，并给出材料保留与 Git 处理建议。

## 确认范围与依据

确定本轮知识主题、后续使用者和文档写入范围。读取项目文档约定、已有正式记录及相关来源，沿引用补齐判断所需的材料。涉及 Matt skills 的产物或配置时，先读取 [Matt 文档职责](references/matt-documents.md)，再按项目实际配置定位资料。

先按实际内容、持续维护方式和在用引用，识别已有材料承担的正式知识维护与来源证据职责。已承担长期维护职责的 Spec、研究笔记或其他文档，优先作为正式维护位置，完整保留原始证据和仍被依赖的内容。仅作为来源的 Spec、任务、决定地图和实验记录，默认只给处理建议；它们的更正、归档、删除和任务状态变更由后续明确指令处理。

以已确认需求和决定判断有效约定，以交付、验收、研究和排障证据判断已实现或已验证的范围；必要时定向读取代码、测试或契约。结论保留其环境、时间、前提与限制，摘要和任务状态用于定位具体依据。

涉及功能交付时，沿用已有整体验收结论或用户对实际已交付结果的明确确认。只有子任务完成记录时，说明整体依据的缺口。研究、排障和技术验证的结论可以按已有证据独立沉淀。

材料冲突时，查找明确的替代或裁决依据。仍无法确定的内容作为具体未决项返回，继续整理不受影响的部分。记录事实与作出决定分别处理；文档整理承接已有决定和验证结论。

## 维护正式知识文档

按知识主题选择已有维护位置：领域词汇、功能行为、外部契约、架构与重要决定、操作说明或研究结论。对项目明确规定须通过专门维护入口或协议修改的载体，本 skill 只读取和引用；需要更新时，将目标位置、具体改动及依据交给对应维护入口，写入和确认遵循该入口的协议。

每条完整约定只有一个正式维护位置，其他入口使用明确引用。现有材料已充分承载知识时，直接沿用；需要补充时优先原位更新，只修改受影响部分，保留仍然有效的知识。

新增文档或索引前，说明现有载体无法满足的具体阅读或维护需要。确需新增时按项目约定选择位置；没有约定时使用 `docs/knowledge/<topic>.md`。

围绕后续读者需要回答的问题组织正文，按需覆盖：

- 当前有效的含义、行为或结论，以及适用范围。
- 理解或使用它所必需的规则、契约、操作、异常与边界。
- 有长期价值的决定理由、可核对的证据和具体未决项。

区分业务要求、外部契约与本项目的实现选择、配置和技术限制，写清后者的适用范围与必要入口。跨项目读者应能识别需要沿用的要求，以及需要在目标项目重新验证或决定的部分。正文及其明确引用共同承载完整知识，开发期材料只承担已说明的来源和证据职责。

正文直接表达当前有效语义。开发顺序、阶段任务和版本替代过程留在原记录中。本轮整理只承接已确认的约定。

## 给出已有材料处理建议

对本轮涉及的已有材料，逐份或按相同理由分组，分别给出保留与 Git 处理建议。按内容价值和实际依赖判断是否保留：

- **继续保留**：仍承载独有的有效约定、未决问题所需证据，或仍被后续任务、验收和外部链接依赖。
- **可以退出活跃文档**：有效内容已完整进入明确的正式位置，在用引用已妥善承接，且需要追溯的来源仍可访问。说明承接位置及尚需完成的动作。

Git 建议依据项目约定、当前跟踪与修改状态、协作访问及追溯需要，明确首次纳入、提交已有修改、维持现状或无需纳入，并说明理由与实际承接位置。

概述不能替代下游依赖的具体字段、协议、实验记录或验收条件。无法确认内容已完整承接或引用已迁移时，保留原材料并说明缺口。已经存在且可访问的 Git 或任务系统历史可作为追溯来源；是否需要另行归档取决于项目约定和实际访问需要。

## 完成检查与交付

重读实际文档，核对有效知识的覆盖与适用范围、约定的唯一维护位置、引用可达性，以及已有材料的保留与 Git 建议是否符合实际依赖和访问需要。有未决项时明确本轮完成的范围，保留继续处理所需的来源。

回复给出选定的正式维护位置及理由、实际更新、待交接的维护事项、已有材料的保留与 Git 处理建议和未决项。无需修改文档时，也完成已有材料判断并明确说明结论。
