# 需求拆分判断与落实

task-steward 判断已有需求是否需要拆分，并落实必要的任务拆分。目标是找到对后续交付有意义、证据边界清楚，且拆开确实改善后续工作的任务边界。

输入为已有需求，不限定来源或载体。原需求的目标、范围、约束和验收要求是拆分依据，保持其原义与完整性。拆分只组织执行边界；未决业务或架构决定返回上游，不通过拆分补齐。

写入限于本轮授权的拆分结果、相关引用、已有索引及拆分记录。不调度、执行或集成实现，不因拆分将功能标记为完成。

## 输入与记录位置

读取原需求、本轮授权范围、必要项目上下文及已有拆分结果与记录；沿用来源标识和引用，不复制完整需求或任务正文。首次读取整体；复审读取来源变化及受影响的拆分内容，保留仍有效的内容与交付证据。

拆分结果沿用项目现有约定或调用方指定的承载方式，每个 task 应可明确引用。没有可确定的写入位置时，返回未保存的 Markdown 草稿并说明原因。

记录固定为 `<feature-workspace>/decomposition.md`，依次使用调用方指定目录、来源或现有记录能确认的需求 workspace；尚无 workspace 但 feature 标识已确认时，按需创建项目根目录下的 `.scratch/<feature>/`。

同一需求只维护一份记录，复审更新原文件；沿用已确认的 feature 标识，原需求保持原位，记录不写入 skill 安装目录。无法唯一定位或位置冲突时，返回未保存的 Markdown 草稿并说明原因，保留现有文件。

## 能不能拆

候选 task 须同时满足以下条件：

* **承诺边界明确**：实现型 task 有明确的行为或成果契约；验证型 task 有明确问题、已知约束、证据要求和判断完成的标准。
* **有独立成果或证据**：完成后留下可被后续工作可靠消费的实现成果或验证证据，并在维持原契约的情况下具有独立价值。成果不要求用户可见，单纯代码片段或更小的 Review 范围不足以成立 task。
* **能够独立验证**：在明确的证据边界内，对本 task 承诺的成果作出完整判断。允许依赖已确认契约，不能依赖尚未确认的未来设计。可以使用 stub、fake 或契约测试建立环境，但其结论不能扩展为尚未发生的真实组合行为。

技术验证 task 可以只交付可复现实验与结论。“方案不可行”可以是成功交付，取决于明确的问题是否已被可靠回答；仍无法回答时保留证据缺口。验证结论不自动授权更换方案、改变需求或架构。开放式探索先返回上游明确问题与完成标准。

能力、数据、接口、状态机、事务、生命周期和集成边界可作为寻找候选成果的信号，不要求 task 属于其中某一类。同一机制的异常和边界、单独的技术步骤或验收项，不因能分别测试就成为独立 task。

## 值不值得拆

合格的候选边界只说明可以拆。先识别当前实现、审查或后续推进的主要困难，再依据已知契约、代码与依赖关系形成具体候选划分，与保持当前范围双向比较。通常优先关注审查有效性和方向控制，并结合当前场景确定主导因素。

逐维度检查以下收益与代价，再综合判断；维度用于防止遗漏，不按满足项数或固定评分决定拆分，也不以文件数、行数或验收项数量设阈值。

| 维度 | 比较重点 |
| --- | --- |
| 审查有效性 | 人和 AI 能否识别、聚焦并覆盖关键契约及交互；拆分能否减少需同时判断的问题，让后续审查复用已确认结论 |
| 整体一致性 | 局部成果与组合证据能否完整承接原需求；跨边界行为如何验证，是否引入遗漏或重复工作 |
| 方向与未知性 | 阶段成果或验证证据能否让调用方在继续投入前确认方向、消除关键未知或调整后续任务 |
| 返修与变更耦合 | finding 能否隔离修复与复审；哪些修改需要跨 task 联动，使既有结论需要重新核对 |
| 风险与发布 | 是否存在需要独立验证、上线或回滚的实际边界，拆分能否隔离对应风险 |
| 下游推进 | 能否提前提供可信基础、解锁下游或支持实际并行；交接和已有人工 gate 如何影响依赖链上的等待 |
| 执行与交接成本 | 比较上下文重建、agent 与人工 Review 次数、证据交接，以及当前执行周期内实际需要的中断恢复或换人接手成本 |

关键取舍须说明因果：当前困难是什么，候选边界通过什么成果或证据改善它，仍有哪些负担或新增代价。共享上下文、分段审查和局部返修的价值，同样要依据当前契约与交互判断。方向确认沿用调用方已有权限和流程。

## 三种判断结果

对原需求与受影响的 task 分别记录判断及依据，标记只使用以下三种：

| 标记 | 判定与动作 |
| --- | --- |
| `ready` | 信息充分，缺少合格拆分边界或具体收益不足以支持拆分；保留原需求并说明判断，不生成 task，不为追求最小粒度继续寻找切口 |
| `needs-split` | 存在可从当前范围独立拆出的合格成果边界，且具体拆分收益足以抵消耦合与流程成本；说明边界、收益及取舍 |
| `cannot_verify` | 缺少决定性信息，无法作出有效判断；说明缺口、影响范围及需返回上游的问题 |

这些标记只表达拆分判断，不授予执行许可，也不表示依赖满足、问题全部解决或功能完成。缺口只影响相应范围，保留其他已有依据的判断。

## 必要时落实

1. **明确平级 task**：对值得拆分的范围，按上述定义写清各 task 的承诺边界与成果、前置依赖及所需交付、验收条件和来源引用。有独立的集成或组合验证工作时，将其作为普通 task，依赖实际所需的交付。操作顺序不自动成为开发先后关系。
2. **保留未决范围**：只有部分方案可确定时，只落实承诺明确的验证 task 和不受结果影响的其他 task。对依赖验证结果或后续决定才能确定的部分，记录未决范围及决策前置，暂不生成确定的执行 task；取得证据并由调用方作出必要决定后，再补全受影响部分。
3. **核对整体覆盖**：核对 task 集合及未决范围是否完整对应原需求，有无遗漏、非预期的重复工作或依赖环。已有 task 需要继续拆细时，同样检查边界与收益，并将结果整理到同一平级集合。拆分时核对的是需求承接；最终整体交付核对由调用方组织，不因 task 完成而自动通过。
4. **写入并复核**：只评审时返回建议；已有落实授权时，按指定或现有约定写入结果及相关引用，同步受影响的已有索引。已有结果先核对并复用，仅更新受影响内容。重读实际结果，复核承诺、前置依赖、验收条件与需求覆盖，再更新拆分记录。

## 记录与回复

记录使用 Markdown，包含来源引用、三种判断结果之一及其依据。说明主导判断的维度、事实依据和因果取舍；保持整体时说明已识别的关键复杂度如何得到处理，需要拆分时说明合格边界、具体收益与代价，并引用平级 task、前置依赖和整体覆盖结论。各维度逐一考虑，记录聚焦决定性因素，不要求固定对比表。分别表达来源事实、评审结论和拆分建议，未落实的内容保持建议状态。

复核已有记录时按当前依据更新判断。来源变化后重评受影响范围，旧结论失效且无法恢复有效判断时，明确标为 `cannot_verify` 并记录缺口；其他有效结论与无关记录保留。旧问题只有新材料证明已解决才移除。

只有实际拆分结果、相关引用、已有索引与拆分记录一致，原需求整体覆盖核对通过，且不存在尚未确定的拆分范围时，才报告整体拆分完成。局部已落实但仍有未决范围时，分别报告两者及其前置，不能以局部落实代替整体完成。写入或核对受阻时，说明已完成的改动、未完成事项与阻塞原因，保留继续处理所需的实际引用。

回复说明判断结果及依据、记录位置或未保存草稿、主要变化、未决范围与后续动作；区分无需拆分、尚无法判断、方案已建议、局部或整体拆分已落实，以及功能交付状态。
