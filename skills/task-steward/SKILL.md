# 需求拆分判断与落实

task-steward 判断已有需求是否需要拆分，以研发执行边界组织任务，通过逐项与集合复核调整划分，并落实必要的任务拆分。

任务边界由工程实现关系形成；未知、风险和执行条件可以调整边界；验证与审查只检查边界，不负责生成边界。

输入为已有需求，不限定来源或载体。原需求的目标、范围、约束和验收要求是拆分依据，保持其原义与完整性。拆分只组织执行边界；未决业务或架构决定返回上游，不通过拆分补齐。

调用方指定的需求是本轮授权根（stewardship root，以下简称根需求）。所有形成、复核和持久化的任务划分都位于根需求内；原需求、当前范围、平级集合及整体完成均以此为界。上游及兄弟需求作为只读上下文，需要调整的事项返回调用方。

写入限于归属根需求且获本轮授权的拆分结果、引用、索引及拆分记录；关联关系不授予写入权限。不调度、执行或集成实现，不因拆分将功能标记为完成。

## 输入与记录位置

先确认根需求及本轮授权范围，再读取其需求、必要项目上下文及已有拆分结果与记录，区分归属根需求的产物与只读来源；沿用来源标识和引用，不复制完整需求或任务正文。首次读取根需求整体；复审读取来源变化及根需求内受影响的拆分内容，保留仍有效的内容与交付证据。

拆分结果沿用项目现有约定或调用方指定的承载方式，每个 task 应可明确引用。没有可确定的写入位置时，返回未保存的 Markdown 草稿并说明原因。

记录固定为 `<root-workspace>/decomposition.md`。先确认 workspace 与记录归属根需求，再依次使用调用方指定目录、来源或现有记录能确认的根需求 workspace；尚无 workspace 但根需求标识已确认时，按需创建项目根目录下的 `.scratch/<root>/`。

同一根需求只维护一份记录，复审后更新归属于本轮需求范围且获授权的拆分记录；沿用已确认的根需求标识，原需求保持原位，记录不写入 skill 安装目录。记录归属或保存位置无法确定、无法唯一定位或位置冲突时，返回未保存的 Markdown 草稿并说明原因，保留现有文件。

## 迭代组织任务

根需求及其已有拆分都按以下顺序复核，具体判断依据见后文。范围外的依赖保留为前置契约和来源引用，需要调整时返回调用方。

1. **先形成边界**：从当前范围的实现目标与工程关系识别候选边界，说明各项需要共同完成的核心设计、预期实现成果及真实依赖。
2. **再修正边界**：结合关键未知、发布或回滚风险及拆分造成的工程问题，调整候选范围与前置关系，保留需要上游决定的未决范围。
3. **最后检查边界**：逐项检查当前范围、各候选和剩余范围的承诺与验证安排；集合检查需求覆盖、重复工作、依赖环及局部与组合验收的承接。分别给出三种判断结果之一。
4. **局部迭代**：检查发现问题时，回到工程关系与修正条件定位原因，拆分、合并或调整边界，重评受影响项及其依赖，保留仍有效的判断，并将结果整理到同一平级集合。逐项与集合检查均有当前事实支持、已识别的重要候选边界均已评估，且没有待处理的边界问题时，当前划分收敛。缺决定性信息的范围保留 `cannot_verify` 和决策前置，其他范围继续复核；局部确定不代表整体收敛。

未拆分的原需求同样经过这三个判断阶段。一个候选边界不成立，仍需评估当前事实支持、可能改变结论的其他重要边界，无需穷举所有划分。这里判断任务定义、实现承接与验证安排是否合适，不要求实现已经完成；迭代由发现的问题驱动，不设固定轮数，也不追求最优或最小粒度。

## 形成边界：工程实现关系

以当前需求和必要项目事实为依据，判断哪些工作构成自然的工程变更单元：

* **自然实现闭环**：围绕同一实现目标，哪些行为、状态转换、异常处理和资源生命周期需要一起完成，才能留下可被后续工作直接使用的实现成果。
* **核心设计耦合**：哪些工作需要共同确定核心状态、模块职责、事务或生命周期；原需求内已知的后续工作，是否必须重新打开前项的核心设计。必然重做核心设计，或前项必须预埋大量仅供下一任务使用的未接通设计时，优先将这些工作放在同一实现单元。共用模块时，进一步区分共同设计与通过既定接口独立扩展。
* **依赖顺序与成果承接**：前项能否形成后项可直接依赖的实现成果，依赖关系是否真实、明确，后项能否在维持前项核心设计与契约的情况下继续实现。存在可并行工作时，据这些关系确认其独立性；并行本身不生成任务边界。

成果可以是用户能力、内部模块或集成能力，不要求用户可见。技术步骤和验收场景按其所属的实现闭环组织；文件数、行数或验收项数量不决定任务粒度。

## 修正边界：未知、风险与执行条件

在候选工程边界上判断以下条件是否要求调整范围或依赖，并说明触发调整的事实与因果：

* **关键未知**：未知会改变实现路线或核心设计时，将已明确问题、约束和完成标准的技术验证作为决策前置；受其影响的实现范围保留未决，不受影响的工作继续复核。方向与架构决定沿用调用方已有权限和流程。
* **发布与回滚风险**：存在实际的独立上线、回滚或风险隔离要求时，核对候选成果能否承担对应责任，据此调整边界及依赖。
* **拆分造成的工程问题**：检查候选划分是否制造临时合同、重复修改或异常高的上下文重建，将问题追溯到被切开的实现关系并修正边界。执行与交接成本只用于这类修正，不以正常交接、审查次数或等待成本否定已成立的自然实现边界。

执行条件以当前项目或调用方已确认的流程为依据。事实缺口影响边界判断时，说明受影响范围；缺少决定性信息的范围使用 `cannot_verify`，其余有依据的判断保留。

## 检查边界：承诺、验证与集合覆盖

候选 task 须同时满足以下条件：

* **承诺边界明确**：实现型 task 有明确的行为或成果契约；验证型 task 有明确问题、已知约束、证据要求和判断完成的标准。
* **有独立成果或证据**：完成后留下可被后续工作可靠消费的实现成果或验证证据，并在维持原契约的情况下具有独立价值。单纯代码片段或更小的 Review 范围不足以成立 task。
* **结果可确认**：在明确的前置依赖契约和证据边界内，能够验证与审查本 task 承诺的成果；不要求脱离前置 task 运行。允许依赖已确认契约，不能依赖尚未确认的未来设计。可以使用 stub、fake 或契约测试建立环境，但其结论不能扩展为尚未发生的真实组合行为。

技术验证 task 可以只交付可复现实验与结论。“方案不可行”可以是成功交付，取决于明确的问题是否已被可靠回答；仍无法回答时保留证据缺口。验证结论不自动授权更换方案、改变需求或架构。开放式探索先返回上游明确问题与完成标准。

集合检查核对 task 及未决范围是否完整承接原需求，有无遗漏、非预期重复或依赖环。明确局部验收与组合验收各自证明什么、由哪项工作承接，区分已有证据与待前置 task 完成后才能取得的证据；契约或实现变化时重评受影响结论。独立的集成或组合验证工作同样经过边界形成、修正和检查，不能仅因验证对象不同就单列 task。

## 三种判断结果

对原需求与各候选或受影响的 task 范围分别记录判断及依据，标记只使用以下三种：

| 标记 | 判定与动作 |
| --- | --- |
| `ready` | 信息充分，当前范围的边界经过形成、修正与检查后成立，重要候选边界已评估，无需进一步拆分；原需求无需拆分时保留原需求并说明判断，不生成 task |
| `needs-split` | 当前范围包含应分别承接的实现闭环，或需先独立解决影响后续路线的关键未知；候选边界经修正与检查成立，说明各项成果与真实依赖 |
| `cannot_verify` | 缺少决定性信息，无法作出有效判断；说明缺口、影响范围及需返回上游的问题 |

这些标记只表达对应范围的拆分判断，不授予执行许可，也不表示依赖满足、问题全部解决或功能完成。各项判断与集合是否收敛分别说明。缺口只影响相应范围，保留其他已有依据的判断。

## 必要时落实

1. **明确平级 task**：将已通过复核的划分写清为各 task 的承诺边界与成果、前置依赖及所需交付、验收条件和来源引用。边界成立的独立集成或组合验证工作作为普通 task；操作顺序不自动成为开发先后关系。
2. **保留未决范围**：只有部分方案可确定时，只落实承诺明确的验证 task 和不受结果影响的其他 task。对依赖验证结果或后续决定才能确定的部分，记录未决范围及决策前置，暂不生成确定的执行 task；取得证据并由调用方作出必要决定后，再复核受影响范围及其与集合的关系。
3. **写入并复核**：只评审时返回建议；已有落实授权时，核对写入对象归属根需求且在授权范围内，按指定或现有约定写入结果及引用，同步根需求内获授权的已有索引。已有结果先核对并复用，仅更新受影响内容。重读实际结果，核对其与当前划分、依赖和需求覆盖结论一致，再更新根需求的拆分记录。

拆分时核对的是实现边界、需求承接与验证安排；最终整体交付核对由调用方组织，不因 task 完成而自动通过。

## 记录与回复

记录使用 Markdown，明确根需求及其来源引用，保留当前有效划分、决定性依据及未决范围，不保存各轮过程。包含各范围的判断及依据、平级 task 与前置依赖引用、需求覆盖和集合检查结论。先说明形成边界的工程关系，再说明实际修正因素及检查结果：保持整体时说明需要共同完成的实现闭环与核心设计，拆分时说明各项成果如何独立成立和相互承接。技术验证说明其要回答的问题及影响的后续决定。记录聚焦决定性事实与因果，不要求固定对比表。分别表达来源事实、评审结论和拆分建议，未落实的内容保持建议状态。

复核已有记录时按当前依据更新判断。来源变化后重评受影响范围，旧结论失效且无法恢复有效判断时，明确标为 `cannot_verify` 并记录缺口；其他有效结论与无关记录保留。旧问题只有新材料证明已解决才移除。

只有当前划分已收敛，实际拆分结果、相关引用、已有索引与拆分记录一致，且不存在尚未确定的拆分范围时，才报告整体拆分完成。局部已落实但仍有未决范围时，分别报告两者及其前置，不能以局部落实代替整体完成。写入或核对受阻时，说明已完成的改动、未完成事项与阻塞原因，保留继续处理所需的实际引用。

回复说明各范围判断及依据、当前划分是否收敛、记录位置或未保存草稿、主要变化、未决范围与后续动作；区分无需拆分、尚无法判断、方案已建议、局部或整体拆分已落实，以及功能交付状态。
