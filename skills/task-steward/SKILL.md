# 需求拆分判断与落实

task-steward 判断已有需求是否需要拆分，并落实必要的任务拆分。无需拆分时保留原需求并说明判断；需要时拆成多个平级 task，明确各自的范围、前置依赖和验收条件，并核对对原需求的整体覆盖。

只评审时将拆分方案保留为建议；落实时，写入限于本轮授权的拆分结果、相关引用、已有索引及拆分记录。不调度、执行或集成实现，不因拆分将功能标记为完成。

输入为已有需求，不限定来源或载体。原需求的目标、范围、约束和验收要求是拆分依据，保持其原义与完整性；超出既定范围的问题返回调用方。

## 输入与记录位置

读取原需求、本轮授权范围、必要项目上下文及已有拆分结果与记录；沿用来源标识和引用，不复制完整需求或任务正文。

拆分结果沿用项目约定的承载方式。每个 task 应可明确引用，载体按当前交接与追踪需要选择。没有可确定的写入位置时，返回未保存的 Markdown 草稿并说明原因。

记录固定为 `<feature-workspace>/decomposition.md`，依次使用调用方指定目录、来源或现有记录能确认的需求 workspace；尚无 workspace 但 feature 标识已确认时，按需创建项目根目录下的 `.scratch/<feature>/`。

同一需求只维护一份记录，复审更新原文件；沿用已确认的 feature 标识，原需求保持原位，记录不写入 skill 安装目录。无法唯一定位或位置冲突时，返回未保存的 Markdown 草稿并说明原因，保留现有文件。

## 拆分判断

对原需求的工作范围判断粒度；已有拆分时，同时核对各 task 的范围。粒度只使用以下标记：

| 标记 | 判定 |
| --- | --- |
| 留空 | 材料不足，或旧结论失效后无法恢复有效判断；记录缺口 |
| `ready` | 有依据证明当前范围是一个聚焦、可一次实现并独立验证的闭环 |
| `needs-split` | 仍有多个可分别实现和验证的闭环，指出至少两个作为依据 |

主要工作应围绕同一个状态或生命周期，并在同一行为边界验证。若至少两个部分能分别实现、验证，且一个缺失或错误时另一个仍有独立完成价值，优先判 `needs-split`。具有各自成功、失败和恢复规则的机制通常属于此类；保持原行为契约使其无法独立实现和验证时，保留为一个闭环。

同一机制的场景、异常与边界可分别失败，不因此拆分。不以文件数、行数或验收项数量设硬阈值；拆到仅剩无独立实现和验证意义的技术步骤时停止。

`ready` 只表达粒度判断，不授予执行许可，也不表示依赖满足、问题全部解决或功能完成。材料不足时说明缺口，保留未决判断。

## 评审与落实

1. **理解需求**：核对原需求的目标、范围、约束和验收要求，以及影响拆分的已有交付与前置条件。首次读取整体；复审读取来源变化及受影响的拆分内容，保留仍有效的内容与交付证据。
2. **判断是否拆分**：依据闭环的独立实现与验证价值作出判断。无需拆分时保留原需求并说明判断，不生成 task；需要拆分时指出独立闭环及依据，进入拆分。缺少决定性信息时记录问题，不能用猜测补齐范围或验收要求。
3. **明确平级 task**：每项写清承接的需求范围、前置依赖与所需交付、验收条件及来源引用。有集成、组合验证或整体验收工作时，将其作为普通 task，依赖实际所需的交付。执行前置按必要交付确定，操作顺序不自动成为开发先后关系；不确定的依赖列为待确认问题。
4. **核对整体覆盖**：确认所有 task 合起来完整承接原需求，没有遗漏、非预期的重复工作或依赖环。各 task 仍须粒度合适；需要继续拆细时，将结果整理到同一平级任务集合中。单项验收与整体需求验收分别核对。
5. **落实并复核**：只评审时返回建议；已有落实授权时，按项目约定写入拆分结果及相关引用，同步受影响的已有索引。已有结果先核对并复用，仅更新受影响内容。重读实际结果，复核范围、前置依赖、验收条件与整体覆盖，再更新拆分记录。

## 记录与回复

记录使用 Markdown，包含来源引用、拆分判断及依据；发生拆分时，引用平级 task、前置依赖和整体覆盖结论。分别表达来源事实、评审结论和拆分建议，未落实的内容保持建议状态。

评审发现只记录需要处理的问题。来源变化时重评，无法恢复有效判断则清空粒度标记；旧问题只有新材料证明已解决才移除，保留无关记录。

只有实际拆分结果、相关引用、已有索引与拆分记录一致，且原需求的整体覆盖核对通过后，才报告拆分完成。写入或核对受阻时，说明已完成的改动、未完成事项与阻塞原因，保留继续处理所需的实际引用。

回复说明是否需要拆分及依据、记录位置或未保存草稿、主要变化、未解决问题及后续动作；区分无需拆分、方案已建议、拆分已落实与功能交付状态。
