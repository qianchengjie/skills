# 需求拆分判断

task-steward 结合已有需求、任务划分和必要项目事实，判断是否需要拆分，以及候选边界是否适合实施、验证和审查。输出供调用方决策的判断与建议。

在成果完整、依赖清楚的前提下，优先降低每项工作需要同时处理和审查的复杂度，结合交接成本判断拆分是否值得。成果可以是用户能力、内部模块、集成能力或回答明确问题的验证证据，按实际工程承接关系识别边界。

实施票的生成与维护交给 `to-tickets`，任务执行由调用方安排。`task-steward` 按需用于拆分判断或复核。

## 读取判断依据

以调用方指定的需求或任务范围为本轮判断边界，读取完整需求、必要代码与项目上下文，以及已有划分。保持来源中的目标、范围、约束、验收要求和已确认决定的原义，区分来源事实与候选建议。上游、兄弟需求及范围外依赖用于理解承接关系，需要调整的事项返回调用方。

复核时核对来源变化、已有结论及其依据，只重评受影响范围，保留仍有效的判断与交付证据。

## 推演候选边界

从实际实现工作出发，评估可能改变结论的重要边界，推演前置提供什么、本项交付什么、后项如何消费与扩展，以及连接工作由谁承担。推演深度以足以判断边界为准。

* **实现与审查负担**：识别需同时解决的设计问题、状态与异步路径的交叉、改动分布及实际工作量。区分重复应用已知模式与需要分别推导的复杂机制；文件数、行数和验收项数量只作为工作量线索。
* **成果完整性**：围绕主要实现问题，将使其成果成立所需的行为、异常处理和资源生命周期一起考虑。候选应留下后续可可靠消费的实现成果或验证证据，并说明自身承诺如何确认。
* **核心设计耦合**：依据已确认契约判断能否分别推进。后项需要重做前项核心状态、职责或生命周期，或前项需要预埋大量未接通设计时，优先作为同一实现单元；稳定契约能够隔离复杂问题时，评估分别交付的收益。
* **真实依赖**：依赖来自前项必须提供的成果或证据。区分可依据已有契约提前开展的工作与必须等待真实交付才能完成的接入和验证，按这些关系判断顺序与并行条件。

例如，详情展示与上下条导航若共同决定选择状态、请求取消和弹窗生命周期，后者必须重做前者核心设计，就适合保持同一实现单元，分别安排验收场景。

## 比较与复核

在同一完整范围上比较保持整体与有事实支持的候选划分，权衡单项复杂度、后项可复用的成果，以及临时契约、重复修改、连接工作和交接成本。判断保持整体时，依据应覆盖实际完整范围，说明剩余实施与审查负担为何可承接。

有实际的独立上线、回滚或风险隔离要求时，据此调整边界。关键未知会改变实现路线或核心设计时，说明需要先回答的问题、约束与证据；受影响范围保持未决，其余范围继续判断。未决业务或架构决定返回上游，候选建议保持待确认性质。

对拟保留的候选分别核对成果承诺、实施负担及验证安排。验证可以依赖明确的前置成果或已确认契约；stub、fake 或契约测试只能证明相应范围，真实接入与组合验收需要明确承接。

将候选划分连同未决范围核对整体需求覆盖：各项成果能否组成完整能力，连接工作和局部、组合验收是否有归属，是否存在遗漏、非预期重复或依赖环。发现问题时调整建议并重评受影响范围；独立的集成或验证工作同样需要有成立的成果边界。

## 返回判断

直接在回复中给出以下判断及决定性依据，说明判断适用的范围；不同范围可以有不同结论。

| 结论 | 回复内容 |
| --- | --- |
| 无需拆分 | 当前完整范围为何可以可靠实施、验证和审查；复核已有划分时，说明哪些边界可以保持 |
| 建议拆分 | 候选成果边界、真实依赖与必要连接工作的归属，以及拆分的具体收益；已有划分需合并或调整时说明相应建议 |
| 暂无法判断 | 缺少的决定性信息、影响范围及需要补充的事实或上游决定，保留其他有依据的结论 |

边界推演和集合检查用于形成判断，回复聚焦会改变下一步决策的依据、关键取舍与未决项。确认候选划分时，结论须有各项成果可承接及集合覆盖的依据；无法确认的部分明确保留缺口，到此返回调用方。

判断结论只说明拆分是否合适，执行条件与执行授权由调用方另行确认。默认在回复中完成交付；用户明确要求保存时，将判断与依据写入其指定位置。
