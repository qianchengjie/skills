# 需求拆分判断与落实

task-steward 判断已有需求是否需要拆分，将需求组织为能够可靠实施、验证和审查的工作单元，通过逐项与集合复核调整划分，并落实必要的任务拆分。

以工程实现关系识别候选边界。在成果完整、依赖清楚的前提下，优先降低每项任务需要同时处理和审查的复杂度。能够通过稳定契约分开解决的问题，允许付出适度交接成本分别交付；保留整体需要说明合并后的负担为什么可承接。

输入为已有需求，不限定来源或载体。原需求的目标、范围、约束和验收要求是拆分依据，保持其原义与完整性。拆分只组织执行边界；未决业务或架构决定返回上游，不通过拆分补齐。

调用方指定的需求是本轮授权根（stewardship root，以下简称根需求），本轮持续复核候选内部边界时保持不变。只有调用方在另一次调用中明确指定某个候选为授权对象时，该候选才成为那次调用的根需求。所有形成、复核和持久化的任务划分都位于根需求内；原需求、当前范围、平级集合及整体完成均以此为界。上游及兄弟需求作为只读上下文，需要调整的事项返回调用方。

写入限于归属根需求且获本轮授权的拆分结果、引用、索引及拆分记录；关联关系不授予写入权限。不调度、执行或集成实现，不因拆分将功能标记为完成。

## 输入与记录位置

先确认根需求及本轮授权范围，再读取其需求、必要项目上下文及已有拆分结果与记录，区分归属根需求的产物与只读来源；沿用来源标识和引用，不复制完整需求或任务正文。首次读取根需求整体；复审读取来源变化及根需求内受影响的拆分内容，保留仍有效的内容与交付证据。

拆分结果沿用项目现有约定或调用方指定的承载方式，每个 task 应可明确引用。没有可确定的写入位置时，返回未保存的 Markdown 草稿并说明原因。

记录固定为 `<root-workspace>/decomposition.md`。先确认 workspace 与记录归属根需求，再依次使用调用方指定目录、来源或现有记录能确认的根需求 workspace；尚无 workspace 但根需求标识已确认时，按需创建项目根目录下的 `.scratch/<root>/`。

同一根需求只维护一份记录，复审后更新归属于本轮需求范围且获授权的拆分记录；沿用已确认的根需求标识，原需求保持原位，记录不写入 skill 安装目录。记录归属或保存位置无法确定、无法唯一定位或位置冲突时，返回未保存的 Markdown 草稿并说明原因，保留现有文件。

## 迭代组织任务

对根需求、已有拆分，以及本轮每个新形成或调整的候选与剩余范围，完整执行以下前三个判断阶段，再检查整个候选集合。

判断以根需求原文、授权边界、当前范围和必要项目事实为依据，核对前后项需承接的契约。已确认的业务、架构与测试决定保持完整；拆分建议中的契约明确为待核实建议。范围外的依赖保留为前置契约和来源引用，需要调整时返回调用方。

1. **先形成边界**：从当前实现及已确认契约出发，识别实际实现工作与复杂度，评估当前范围内部的重要候选边界，推演候选交付与后续接入，据此形成任务范围及真实依赖。
2. **再修正边界**：比较保持整体与拆分的工程代价，结合关键未知、发布或回滚风险调整候选范围与前置关系，保留需要上游决定的未决范围。
3. **最后检查边界**：检查本范围的成果承诺、实施负担及验证与审查安排，结合前两个阶段给出三种判断结果之一。
4. **局部迭代与集合检查**：遇到 `needs-split` 或检查发现的边界问题时，依据工程关系与修正条件拆分、合并或调整，对每个新形成或受影响的候选从第一阶段开始判断，保留仍有效的判断。将必要调整整理为根需求下的同一平级 task 集合，连同未决范围检查各项成果如何承接并组成根需求要求的完整能力，以及需求覆盖、重复工作、依赖环和局部与组合验收的承接；集合发现问题时同样重评受影响范围。

复用已有判断前，核对范围、契约和依据仍有效；补查改变结论的事实或契约后，只重评受影响范围。

只有根需求内每个最终候选的重要内部边界均已评估、完整判断确认当前粒度适合实施与审查、无需进一步拆分且通过边界检查，必要调整已整理为同一平级集合并通过集合检查，且无未决阻塞时，当前划分才算收敛。缺决定性信息的范围保留 `cannot_verify`、缺口及决策前置，并阻断整体收敛；其余范围继续复核，保留有效结论，直到收敛或明确留下阻塞范围。

一个候选边界不成立，仍需评估当前事实支持、可能改变结论的其他重要边界，无需穷举所有划分。这里判断任务定义、实现承接与验证安排是否合适，不要求实现已经完成；不设固定轮数，也不追求最优或最小粒度。

## 形成边界：实现工作、复杂度与成果承接

以当前需求和必要项目事实为依据，从当前实现及已确认契约出发，沿候选依赖推演各项完成后的成果及后续接入：前置提供什么，本项改变并交付什么，后项如何消费与扩展，以及连接工作由哪项承担。核对每项在所述实现状态下能否履行自身承诺；对已识别的重要内部边界，依据分开实现后的具体承接关系或必须重做的核心设计，决定保留或调整范围。推演深度以足以判断边界为准，不要求提前完成详细实现设计。

* **实现与审查负担**：识别需同时解决的设计问题、状态与异步路径的交叉、改动分布及实际工作量。区分重复应用已知模式与需要分别推导的复杂机制，说明已有模式覆盖哪些问题，其余问题能否通过稳定契约分别解决。
* **自然实现闭环**：围绕一项主要实现问题形成候选，将使其成果成立所需的行为、状态转换、异常处理和资源生命周期一起完成。任务承诺按其实际交付范围界定，后续接入与完整需求由相应任务承接；据此检查哪些连接工作是本项成果成立所必需，哪些可以消费该成果独立推进。
* **核心设计耦合**：区分机制自身的不变量与调用方接入的覆盖要求。状态或协议的所有者交付完整行为契约，调用方通过该契约接入时，分别评估两者的任务边界。需要共同确定核心状态、职责或生命周期时，先在本轮授权内明确必要契约，再判断能否分别实施；后项必然重做前项核心设计，或前项必须预埋大量未接通设计时，优先放在同一实现单元。契约推演以足以判断职责和成果承接为限，未决业务或架构决定返回上游。
* **依赖顺序与成果承接**：前项能否形成后项可直接依赖的实现成果，后项能否在维持前项核心设计与契约的情况下继续实现。较大的同一模块也评估渐进交付：前项兑现较窄但完整的行为契约，后项以扩展能力继续推进；依据具体状态和接口变化判断其是否成立。依赖关系应真实、明确；存在可并行工作时，据这些关系确认独立性，并行本身不生成任务边界。

成果可以是用户能力、内部模块或集成能力，不要求用户可见。技术步骤和验收场景按其所属的实现闭环组织；文件数、行数和验收项数量作为工作量线索，结合模式重复程度和已知执行条件判断。

## 修正边界：未知、风险与执行条件

在候选工程边界上判断以下条件是否要求调整范围或依赖，并说明触发调整的事实与因果：

* **关键未知**：未知会改变实现路线或核心设计时，将已明确问题、约束和完成标准的技术验证作为决策前置；受其影响的实现范围保留未决，不受影响的工作继续复核。方向与架构决定沿用调用方已有权限和流程。
* **发布与回滚风险**：存在实际的独立上线、回滚或风险隔离要求时，核对候选成果能否承担对应责任，据此调整边界及依赖。
* **整体与拆分的工程代价**：对有事实支持的重要内部边界，先将最有价值的进一步划分推演成可交付任务，明确各项完整承诺、前后承接及连接与验证的归属。保持当前候选与这一拆法覆盖同一完整范围，比较各项需要同时处理的复杂问题、后项可直接依赖的结论，以及临时契约、重复修改、连接工作与交接成本。按降低单项复杂度的优先级取舍；保留整体的依据应覆盖其实际完整范围，说明剩余负担为何可承接，以及继续拆分的收益为何不足以支持调整。

执行条件以当前项目或调用方已确认的流程为依据。事实缺口影响边界判断时，说明受影响范围；缺少决定性信息的范围使用 `cannot_verify`，其余有依据的判断保留。

## 检查边界：承诺、验证与集合覆盖

候选 task 须同时满足以下条件：

* **承诺边界明确**：实现型 task 有明确的行为或成果契约；验证型 task 有明确问题、已知约束、证据要求和判断完成的标准。
* **有独立成果或证据**：完成后留下可被后续工作可靠消费的实现成果或验证证据，且成果边界与已确认契约一致。单纯代码片段或更小的 Review 范围不足以成立 task。
* **实施负担可承接**：每个拟判为 `ready` 的候选都给出停止拆分依据：实际完整范围、最有价值的进一步拆法中各项的可交付成果与依赖，以及比较后的取舍。确认本项各组主要工作及其交叉能够可靠实施、调试和审查；依据支持的范围与最终保留的范围一致。
* **结果可确认**：在明确的前置依赖契约和证据边界内，能够验证与审查本 task 承诺的成果；不要求脱离前置 task 运行。允许依赖已确认契约，不能依赖尚未确认的未来设计。沿已确认测试边界验证本项已接通的范围，可以使用 stub、fake 或契约测试建立环境；其结论不能扩展为尚未发生的真实组合行为，剩余接入与组合验收由后续任务承接。

技术验证 task 可以只交付可复现实验与结论。“方案不可行”可以是成功交付，取决于明确的问题是否已被可靠回答；仍无法回答时保留证据缺口。验证结论不自动授权更换方案、改变需求或架构。开放式探索先返回上游明确问题与完成标准。

集合检查沿形成边界时的交付与接入推演，核对各项成果及连接工作的归属是否一致、能否组成根需求要求的完整能力，并检查未决范围、遗漏、非预期重复或依赖环。发现某项承诺在所述实现状态下无法成立、连接工作无人承接或后续必须重开前项核心设计时，回到工程关系调整受影响范围与依赖。

明确局部验收与组合验收各自证明什么、由哪项工作承接，区分已有证据与待前置 task 完成后才能取得的证据；契约或实现变化时重评受影响结论。独立的集成或组合验证工作同样经过边界形成、修正和检查，不能仅因验证对象不同就单列 task。

## 三种判断结果

对原需求与各候选或受影响的 task 范围分别记录判断及依据，标记只使用以下三种：

| 标记 | 判定与动作 |
| --- | --- |
| `ready` | 信息充分，本范围已完成边界形成、修正与检查，已给出覆盖实际完整范围的停止拆分依据，确认实施与审查负担可承接且无需进一步拆分；原需求无需拆分时保留原需求并说明判断，不生成 task |
| `needs-split` | 工程事实支持当前范围需要拆分：通过分别承接实现成果降低实施与审查负担或隔离风险，或需先独立解决影响后续路线的关键未知；说明候选成果与真实依赖，新候选继续完成自身判断 |
| `cannot_verify` | 缺少决定性信息，无法作出有效判断；说明缺口、影响范围及需返回上游的问题 |

这些标记只表达对应范围的拆分判断，不授予执行许可，也不表示依赖满足、问题全部解决或功能完成。各项判断与集合是否收敛分别说明。缺口只影响相应范围，保留其他已有依据的判断。

## 必要时落实

1. **明确平级 task**：将已通过复核的划分写清为各 task 的承诺边界与成果、前置依赖及所需交付、验收条件和来源引用。边界成立的独立集成或组合验证工作作为普通 task；操作顺序不自动成为开发先后关系。
2. **保留未决范围**：只有部分方案可确定时，只落实承诺明确的验证 task 和不受结果影响的其他 task。对依赖验证结果或后续决定才能确定的部分，记录未决范围及决策前置，暂不生成确定的执行 task；取得证据并由调用方作出必要决定后，再复核受影响范围及其与集合的关系。
3. **写入并复核**：只评审时返回建议；已有落实授权时，核对写入对象归属根需求且在授权范围内，按指定或现有约定写入结果及引用，同步根需求内获授权的已有索引。已有结果先核对并复用，仅更新受影响内容。重读实际结果，核对其与当前划分、依赖和需求覆盖结论一致，再更新根需求的拆分记录。

拆分时核对的是实现边界、需求承接与验证安排；最终整体交付核对由调用方组织，不因 task 完成而自动通过。

## 记录与回复

记录使用 Markdown，明确根需求及其来源引用，保留当前有效划分、决定性依据及未决范围，不保存各轮过程。包含各范围的判断及依据、平级 task 与前置依赖引用、需求覆盖和集合检查结论。说明边界的工程关系、主要复杂度及保持整体与拆分的取舍：保持整体时说明仍需同时处理的问题及负担如何承接，拆分时说明各项成果如何减少后项需要处理的问题、独立成立并相互承接。技术验证说明其要回答的问题及影响的后续决定。记录聚焦决定性事实与因果，不要求固定对比表。分别表达来源事实、评审结论和拆分建议，未落实的内容保持建议状态。

复核已有记录时按当前依据更新判断。来源变化后重评受影响范围，旧结论失效且无法恢复有效判断时，明确标为 `cannot_verify` 并记录缺口；其他有效结论与无关记录保留。旧问题只有新材料证明已解决才移除。

只有当前划分已收敛，实际拆分结果、相关引用、已有索引与拆分记录一致，且不存在尚未确定的拆分范围时，才报告整体拆分完成。局部已落实但仍有未决范围时，分别报告两者及其前置，不能以局部落实代替整体完成。写入或核对受阻时，说明已完成的改动、未完成事项与阻塞原因，保留继续处理所需的实际引用。

回复说明各范围判断及依据、当前划分是否收敛、记录位置或未保存草稿、主要变化、未决范围与后续动作；区分无需拆分、尚无法判断、方案已建议、局部或整体拆分已落实，以及功能交付状态。
