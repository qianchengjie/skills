# rules-review：检查项目规则是否得到遵守

项目会积累一些需要在多次开发中持续遵守的规则，例如数据访问边界、状态管理约定或错误处理要求。`rules-review` 对完整的有效规则逐条作出判断，检查调用方指定的代码范围是否违反适用规则。

本文解释规则审查的作用和结论边界；具体执行要求见 [SKILL.md](../skills/rules-review/SKILL.md)。

## 它补充了哪部分审查

[task-review](task-review.md) 从任务要求和具体设计事实寻找问题。项目规则则保存了已经明确、需要反复遵守的约定；即使当前功能运行正常，这些约定仍可能被违反。

规则审查把每个问题连接到具体规则：这条规则为什么适用，代码在哪里承担相应义务，以及实际行为与规则有什么矛盾。这样，调用方能沿着依据复核结论。

## 为什么要完整遍历

如果只挑选看起来与变更有关的规则，遗漏的规则就没有得到判断。“已检查的部分没有问题”无法说明整个有效规则集合的覆盖情况。

完整遍历让结论有明确边界：每条规则都被考虑，适用的检查是否遵守，不适用的有确定依据，缺少事实的保留为未决。只有这些判断完成，才能给出覆盖完整规则集合的结果。

这里的完整针对判断覆盖。规则目录已经给出完整的适用条件，且证据确定条件不成立时，可以直接判断不适用；其余情况需要读取规则正文。目录和正文来自同一来源，避免拿一个版本的适用条件解释另一个版本的要求。

规则通过 [rule-steward](rule-steward.md) 的正式读取工具发现。工具确认没有规则来源，或确认规则集合合法但为空时，可以按无有效规则处理；读取失败则意味着覆盖情况尚不能确定。

## 违反规则与无法判断

判断分成两件事：规则是否在当前情况下生效，以及生效后代码是否满足它。两者都可能因为缺少事实而无法确定。

假设某项目有一条规则：“对外 API 必须校验租户身份。”以下情况会得到不同结论：

| 已有事实 | 可以作出的判断 |
| --- | --- |
| 已确认是对外 API，完整调用路径显示缺少租户校验。 | 规则适用，存在违反。 |
| 已确认是对外 API，但无法取得决定校验行为的网关配置。 | 规则适用，是否符合仍无法判断。 |
| 路由暴露方式不明，无法确定是否是对外 API。 | 是否适用仍无法判断。 |
| 已确认仅供内部调用，不满足这条规则的生效条件。 | 这条规则不适用。 |

`cannot_verify` 保留的是尚未确定的判断，方便调用方补充相应事实。它不会抹去已经确认的问题；同一份审查结果中可以同时存在违反项和无法判断项。

`Clean` 表示代码范围与完整规则集合均可确定，并且每条有效规则都已得到“不适用”或“适用且通过”的结论。它说明本次规则审查的结果，任务正确性和实现设计仍由相应审查负责。

## 规则覆盖与代码范围

完整遍历规则时，代码审查范围仍由调用方指定。审查者可以读取调用关系、配置、测试等上下文来取证，提出的问题则定位在范围内的代码，或本应承担某项义务的位置。

这种分工允许充分理解规则是否适用，同时让调用方清楚本次审查覆盖了哪些代码。

## 与规则维护和任务执行的关系

`rule-steward` 负责规则定义及其维护，`rules-review` 负责依据当前有效规则审查代码。规则本身需要改变时，应回到维护环节处理。

规则审查可以独立使用，也可以由 [execute-task](execute-task.md) 在任务审查之后安排。它返回问题和证据；独立复审、返修权限判断和实现修改由执行流程继续组织。

整套流程见 [项目总览](overview.md)。
