# task-steward：判断需求是否需要拆分

`task-steward` 接收已有需求，判断是否需要拆分，并在授权范围内落实必要的拆分。输入不限定来源或载体。先证明存在合格任务边界，再判断拆开是否有具体收益；信息充分且没有拆分收益时保留原需求并说明判断，不生成 task。

具体执行要求见 [SKILL.md](../skills/task-steward/SKILL.md)。

## 能不能拆：承诺、成果与验证边界

实现型 task 有明确的行为或成果契约；验证型 task 有明确问题、已知约束、证据要求和完成标准。候选 task 应能在维持原契约的情况下，产生后续工作可可靠使用的成果或证据，并对自身承诺形成完整的验证结论。

例如，技术验证可以回答某框架在指定约束下是否可行；可靠的不可行结论也有独立价值。结论供调用方作出后续决定，并不自动授权更换框架或改变需求。

独立验证不要求整个功能已经接通。provider 可以通过契约测试证明自身满足已确认协议，但不能据此宣称它与尚未实现的 consumer 已正确协作；真实组合行为由后续验证证明。

数据、接口、状态机、生命周期等是寻找成果边界的信号。能单独检查一段代码或一个验收项，不足以说明它应当成为 task。

## 值不值得拆：具体收益与流程成本

合格边界只说明可以拆。还要结合变更耦合与下游解锁、返修或风险隔离、独立发布与回滚等具体收益，双向比较拆分与保持整体对 agent Review 和人工 Review 的总成本：单次审查的契约与交互复杂度、finding 后的返修与复审范围，以及拆分增加的交接、上下文重建、审查次数和已有人工 gate 对下游推进的影响。

例如，两种导出格式虽然可以分别实现和测试，但当前由一人完成、没有并行或独立发布需要，拆开只增加交接，就可以保持整体。目标不是尽可能拆小，而是让拆分确实改善后续工作。

## 三种判断结果

| 标记 | 含义 |
| --- | --- |
| `ready` | 有依据支持保持当前范围，无需进一步拆分 |
| `needs-split` | 有可从当前范围独立拆出的合格成果边界，且具体收益足以抵消耦合与流程成本 |
| `cannot_verify` | 缺少决定性信息，记录缺口、影响范围与后续问题 |

`ready` 只表达拆分判断，不表示功能完成或获得执行许可。信息不足时使用 `cannot_verify`，不能把它当作无需拆分。

## 必要时落实

需要拆分时，形成平级 task，明确承诺与成果、前置依赖和验收条件，并核对对原需求的整体覆盖。独立的集成或组合验证作为普通 task；最终整体交付核对由调用方组织，不因 task 完成而自动通过。

技术验证会影响后续路线时，先落实承诺明确的验证 task 及不受结果影响的其他 task。依赖结果或后续决定的部分保留未决范围与决策前置，不能把局部落实报告为整体拆分完成。

拆分结果沿用项目现有约定或调用方指定的承载方式，每项能够被明确引用。无法确定写入位置时，返回未保存的草稿。

## 记录与后续执行

拆分判断保存在需求工作区的 `decomposition.md` 中，记录来源、三种判断结果之一及依据、拆分结果引用和未决范围。需要拆分时说明边界与收益。只请求评审时，方案保留为建议；已有落实授权时，才写入结果并同步相关引用。

复核时沿用有效内容；来源变化使旧结论失效且无法恢复判断时，明确更新为 `cannot_verify` 并说明缺口，保留其他有效结论。拆分结果、引用及记录一致，整体覆盖核对通过且无未确定拆分范围，才报告整体拆分完成。

后续执行由调用方安排，承诺与验收明确的工作交给 [execute-task](execute-task.md)。拆分判断、局部或整体拆分落实，以及功能交付是不同结论。

整套流程见 [项目总览](overview.md)。
