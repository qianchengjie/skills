# task-steward：判断需求是否需要拆分

`task-steward` 接收已有需求，通过迭代复核判断和调整任务边界，并在授权范围内落实必要的拆分。输入不限定来源或载体。先评估当前范围及重要候选边界，再判断是否存在值得采用的调整；信息充分且没有拆分收益时保留原需求并说明判断，不生成 task。

具体执行要求见 [SKILL.md](../skills/task-steward/SKILL.md)。

## 从候选到收敛

首次判断与已有拆分复核采用同一过程：

1. **形成候选**：结合当前承诺、成果、契约与依赖及实际困难，识别当前事实支持、可能改变结论的重要候选边界；有依据支持调整时，形成具体候选划分供比较。
2. **逐项复核**：检查当前范围（包括未拆分的原需求），以及已形成候选划分时的每个候选和剩余范围的资格与收益。明确承诺、前置依赖与验收条件，区分需要首次证明的关键契约和交互、可依赖的前置结论，并说明剩余新增判断为何适合共同完成和审查。
3. **集合与证据分层复核**：检查任务与未决范围对原需求的覆盖、重复工作和依赖环；区分局部验收与组合验收各自承担的证明责任。
4. **局部迭代**：根据发现的问题拆分、合并或调整边界，只重评受影响项及其依赖，保留有效结论，整理为同一平级集合。

组合 task 是正常的任务边界。前置 task 建立稳定可复用的成果与结论，组合 task 聚焦新增的跨边界行为，并按同样标准复核。已有局部证据与待前置 task 完成后才能取得的证据要区分；契约或实现变化时，受影响的结论需要重新核对。跨 task 行为有明确的验证承接，不意味着必须合并任务。

停止依据是：逐项与集合复核都有当前事实支持，已识别的重要边界都已评估，且找不到有充分依据、值得采用的重要调整。审查聚焦由上述新增判断及其关系说明。信息不足的范围保留 `cannot_verify` 和决策前置，其他范围继续复核；局部确定不代表整体收敛。

这一步核对任务定义与证据安排，无需等待实现完成；也不以固定轮数、最优或最小粒度为目标。

## 能不能拆：承诺、成果与验证边界

实现型 task 有明确的行为或成果契约；验证型 task 有明确问题、已知约束、证据要求和完成标准。候选 task 应能在维持原契约的情况下，产生后续工作可可靠使用的成果或证据，并对自身承诺形成完整的验证结论。

例如，技术验证可以回答某框架在指定约束下是否可行；可靠的不可行结论也有独立价值。结论供调用方作出后续决定，并不自动授权更换框架或改变需求。

独立验证允许明确的前置依赖，不要求 task 脱离其他任务运行，也不要求整个功能已经接通。provider 可以通过契约测试证明自身满足已确认协议，但不能据此宣称它与尚未实现的 consumer 已正确协作；真实组合行为由后续验证证明。未决业务或架构决定返回上游，不由拆分补齐。

数据、接口、状态机、生命周期等是寻找成果边界的信号。能单独检查一段代码或一个验收项，不足以说明它应当成为 task。

## 值不值得拆：具体收益与流程成本

合格边界只说明可以拆。将有依据的具体候选划分与保持整体双向比较，合并和调整也比较改善与代价。通常优先关注审查有效性和方向控制，并结合当前场景确定主导因素。

判为 `ready` 前，核对当前事实支持、可能改变结论的重要候选边界；一个划分收益不足，仍需判断其他重要边界，无需穷举所有划分。

比较逐一覆盖七个维度：审查有效性、整体一致性、方向与未知性、返修与变更耦合、风险与发布、下游推进、执行与交接成本。既要考虑人和 AI 能否聚焦关键问题、后续工作能否复用已确认结论，也要考虑跨 task 联动、上下文重建、审查次数与已有人工 gate 对下游的影响。阶段成果用于帮助调用方确认方向或调整后续工作，沿用已有权限和流程。

Review 次数及人工 gate 等待依据当前项目或调用方已确认的执行与审查流程。流程信息未确认时，说明受影响的取舍；只有缺口导致无法有效判断的范围标为 `cannot_verify`，其他有依据的判断保留。

判断须将当前困难、候选边界、预期改善和剩余负担或新增代价连起来，不按维度数量、固定分数或任务规模阈值决定。各维度分别考虑，最终记录突出决定性取舍，无需固定对比表。

例如，两种导出格式虽然可以分别实现和测试，但共同合同简单、局部 finding 已能单独复审，且没有下游解锁或独立发布需要，拆开只增加交接，就可以保持整体。目标不是尽可能拆小，而是让拆分确实改善后续工作。

## 三种判断结果

| 标记 | 含义 |
| --- | --- |
| `ready` | 当前范围适合共同完成和审查，重要候选边界已评估且无足够收益支持进一步拆分 |
| `needs-split` | 有可从当前范围独立拆出的合格成果边界，且具体收益足以抵消耦合与流程成本 |
| `cannot_verify` | 缺少决定性信息，记录缺口、影响范围与后续问题 |

三种结果分别用于原需求与各候选或受影响范围，集合是否收敛单独说明。`ready` 只表达拆分判断，不表示依赖已满足、功能完成或获得执行许可。信息不足时使用 `cannot_verify`，保留其他有依据的判断。

## 必要时落实

需要拆分时，将通过复核的划分落实为平级 task，明确承诺与成果、前置依赖、验收条件和来源引用。独立的集成或组合验证符合资格且值得单列时，作为普通 task；最终整体交付核对由调用方组织，不因 task 完成而自动通过。

技术验证会影响后续路线时，先落实承诺明确的验证 task 及不受结果影响的其他 task。依赖结果或后续决定的部分保留未决范围与决策前置；取得证据并由调用方作出必要决定后，再复核受影响范围及其与集合的关系。

拆分结果沿用项目现有约定或调用方指定的承载方式，每项能够被明确引用。无法确定写入位置时，返回未保存的草稿。

## 记录与后续执行

需求工作区的 `decomposition.md` 保留当前有效划分、决定性取舍及未决范围，不保存各轮过程。记录来源、各范围判断及依据、task 与依赖引用、需求覆盖和集合复核结论。保持整体时说明新增判断为何适合共同完成和审查；调整时说明边界与收益、代价。只请求评审时，方案保留为建议；已有落实授权时，才写入结果并同步相关引用及受影响的已有索引。

复核时沿用有效内容；来源变化使旧结论失效且无法恢复判断时，明确更新为 `cannot_verify` 并说明缺口，保留其他有效结论。当前划分已收敛，实际拆分结果、引用、已有索引及记录一致，且无未确定拆分范围，才报告整体拆分完成；局部落实与未决部分分别说明。

后续执行由调用方安排，承诺与验收明确的工作交给 [execute-task](execute-task.md)。拆分判断、局部或整体拆分落实，以及功能交付是不同结论。

整套流程见 [项目总览](overview.md)。
