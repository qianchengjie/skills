# task-steward：判断需求是否需要拆分

`task-steward` 接收已有需求，以研发执行边界组织任务，通过迭代复核判断和调整划分，并在授权范围内落实必要的拆分。输入不限定来源或载体。当前范围经过边界判断与检查后无需拆分时，保留原需求并说明判断，不生成 task。

具体执行要求见 [SKILL.md](../skills/task-steward/SKILL.md)。

调用方指定的需求是本轮授权根（stewardship root），持续复核候选内部边界时保持不变。只有调用方在另一次调用中明确指定某个候选为授权对象时，它才成为那次调用的根需求。候选形成、平级集合、覆盖复核及持久化均限于根需求；整体收敛与完成也以此为界。上游及兄弟需求作为只读上下文，范围外的依赖保留为前置契约和来源引用，需要调整的事项返回调用方。关联关系不授予写入权限。

## 从候选到收敛

根需求、已有拆分，以及本轮每个新形成或调整的候选与剩余范围，都完整应用以下前三个判断阶段。新生成的拆分项只是候选，尚无自身判断结果；父范围的 `needs-split` 不使新候选默认成立或成为 `ready`。

1. **先形成边界**：从当前实现及已确认契约出发，识别并评估本范围内部的重要候选边界，推演候选交付与后续接入，再根据工程关系形成范围与依赖。
2. **再修正边界**：根据关键未知、发布或回滚风险，以及拆分制造的临时合同、重复修改或异常上下文重建，调整范围与前置关系。
3. **最后检查边界**：检查本范围的承诺、结果能否验证和审查，结合前两个阶段形成判断。
4. **局部迭代与集合检查**：每个新形成或调整的候选在本轮从第一阶段开始判断；需要拆分或检查发现边界问题时，继续调整并重评受影响项及其依赖，保留有效结论。将结果整理为根需求下的同一平级集合，连同未决范围检查各项成果如何承接并组成根需求要求的完整能力，以及覆盖、重复、依赖环和局部与组合验收的承接；集合发现问题时重评受影响范围。

任务边界由工程实现关系形成；未知、风险和执行条件可以调整边界；验证与审查只检查边界，不负责生成边界。

收敛要求根需求内每个最终候选的重要内部边界均已评估、完整判断确认无需进一步拆分且通过边界检查，必要调整已整理为同一平级集合并通过集合检查，且无未决阻塞。缺决定性信息的范围保留 `cannot_verify`、缺口与决策前置，阻断整体收敛；其余范围继续复核并保留有效结论，直到收敛或明确留下阻塞范围。

一个候选不成立，仍需判断其他有事实支持的重要边界，无需穷举所有划分。这一步核对任务定义、实现承接与验证安排，无需等待实现完成；也不以固定轮数、最优或最小粒度为目标。

## 形成边界：从当前实现推演任务边界

沿候选依赖推演前置提供什么、本项改变并交付什么、后项如何消费与扩展，以及连接工作由哪项承担。核对每项在相应实现状态下能否履行自身承诺；评估重要内部边界时，依据分开后的具体承接关系或必须重做的核心设计决定保留或调整。推演到足以判断边界即可，无需提前完成详细实现设计。

自然实现闭环关注围绕同一目标必须共同完成的行为、状态转换、异常处理和资源生命周期，以及完成后可直接使用的实现成果。核心耦合关注哪些工作必须共同确定设计，原需求内已知的后续工作是否必须重开前项核心设计，或迫使前项预埋大量仅供后项使用的未接通设计。共用模块时，要区分共同设计与通过既定接口独立扩展。

前项应能留下后项可直接依赖的实现成果，依赖关系真实、明确。后项通过既定契约继续实现，而非重做前项的核心设计。存在可并行工作时，再根据这些关系确认其独立性；并行本身不生成任务边界。

例如，详情展示与上下条导航若共同决定选择状态、请求取消和弹窗生命周期，后者必须重做前者核心设计，就应作为一个实现任务，分别安排验收场景。成果不要求用户可见，内部模块或集成能力也可以形成实现闭环。

## 修正边界：未知、风险与工程问题

关键未知会改变实现路线或核心设计时，先明确技术验证及后续决定，受影响的实现范围保持未决。存在实际独立上线、回滚或风险隔离要求时，据此调整范围及依赖。

执行条件用于发现拆分制造的工程问题：临时合同、重复修改或异常高的上下文重建。应追溯被切开的实现关系并修正边界，不以正常交接、人工审查次数或等待成本否定已成立的自然实现边界。执行条件依据项目或调用方已确认的流程；缺少决定性事实时，只将受影响范围标为 `cannot_verify`。

## 检查边界：承诺、结果与需求覆盖

实现型 task 有明确的行为或成果契约；验证型 task 有明确问题、已知约束、证据要求和完成标准。候选 task 应能在维持原契约的情况下，产生后续工作可可靠使用的成果或证据，并对自身承诺形成完整的验证与审查结论。

独立验证允许明确的前置依赖，不要求 task 脱离其他任务运行，也不要求整个功能已经接通。provider 可以通过契约测试证明自身满足已确认协议，但不能据此宣称它与尚未实现的 consumer 已正确协作；真实组合行为由后续验证证明。未决业务或架构决定返回上游，不由拆分补齐。

技术验证可以回答某框架在指定约束下是否可行；可靠的不可行结论也有独立价值。结论供调用方作出后续决定，并不自动授权更换框架或改变需求。开放式探索先返回上游明确问题与完成标准。

集合沿交付与接入推演，核对各项成果及连接工作的归属是否一致、能否组成完整能力，以及 task 和未决范围是否完整承接原需求。承诺在相应实现状态下无法成立、连接工作无人承接或后续必须重开前项核心设计时，回到工程关系调整受影响范围与依赖。

局部验收与组合验收须有明确的承接，已有证据与待前置 task 完成后才能取得的证据要区分；契约或实现变化时重评受影响结论。独立集成或组合验证工作同样经过边界形成、修正和检查，不因验证对象不同就单列 task。

## 三种判断结果

| 标记 | 含义 |
| --- | --- |
| `ready` | 本范围已完成边界形成、修正与检查，内部重要候选边界已评估，确认无需进一步拆分 |
| `needs-split` | 工程事实支持当前范围需要拆分，说明候选成果与真实依赖；新候选继续完成自身判断 |
| `cannot_verify` | 缺少决定性信息，记录缺口、影响范围与后续问题 |

三种结果分别用于原需求与各候选或受影响范围，集合是否收敛单独说明。`ready` 只表达拆分判断，不表示依赖已满足、功能完成或获得执行许可。信息不足时使用 `cannot_verify`，保留其他有依据的判断。

## 必要时落实

需要拆分时，将通过复核的划分落实为平级 task，明确承诺与成果、前置依赖、验收条件和来源引用。边界成立的独立集成或组合验证工作作为普通 task；最终整体交付核对由调用方组织，不因 task 完成而自动通过。

技术验证会影响后续路线时，先落实承诺明确的验证 task 及不受结果影响的其他 task。依赖结果或后续决定的部分保留未决范围与决策前置；取得证据并由调用方作出必要决定后，再复核受影响范围及其与集合的关系。

拆分结果沿用项目现有约定或调用方指定的承载方式，每项能够被明确引用。无法确定写入位置时，返回未保存的草稿。

## 记录与后续执行

先确认 workspace 与记录归属根需求，再选择保存位置；尚无 workspace 但根需求标识已确认时，按需创建 `.scratch/<root>/`。根需求工作区的 `decomposition.md` 明确根需求及其来源引用，保留当前有效划分、决定性依据及未决范围，不保存各轮过程。记录各范围判断及依据、task 与依赖引用、需求覆盖和集合检查结论。记录归属或保存位置无法确定、无法唯一定位或位置冲突时，返回未保存草稿并保留现有文件。

记录先说明形成边界的工程关系，再说明实际修正因素与检查结果。保持整体时说明共同实现的闭环与核心设计，拆分时说明各项成果如何独立成立和相互承接；技术验证说明其问题及影响的后续决定。只请求评审时，方案保留为建议；已有落实授权时，写入对象限于归属根需求且获授权的结果、引用、索引及拆分记录。复审后更新归属于本轮需求范围的拆分记录。

复核时沿用有效内容；来源变化使旧结论失效且无法恢复判断时，明确更新为 `cannot_verify` 并说明缺口，保留其他有效结论。当前划分已收敛，实际拆分结果、引用、已有索引及记录一致，且无未确定拆分范围，才报告整体拆分完成；局部落实与未决部分分别说明。

后续执行由调用方安排，承诺与验收明确的工作交给 [execute-task](execute-task.md)。拆分判断、局部或整体拆分落实，以及功能交付是不同结论。

整套流程见 [项目总览](overview.md)。
