# task-steward：判断需求是否需要拆分

`task-steward` 接收已有需求，判断是否需要拆分，并在授权范围内落实必要的拆分。输入不限定来源或载体。无需拆分时保留原需求并说明判断；需要时形成多个平级 task，明确范围、前置依赖和验收条件，并核对对原需求的整体覆盖。

具体执行要求见 [SKILL.md](../skills/task-steward/SKILL.md)。

## 用交付判断是否拆分

是否需要拆分，取决于需求能否形成一个聚焦、可独立验证的实现闭环。一个完整行为可能跨多个模块，同一个文件也可能包含几个独立能力。

例如，单次导入与带重试、恢复机制的批量导入，可能各自具有独立的实现和验收价值。相反，同一次导入的正常输入、错误输入和边界情况，通常共同定义这一能力的完整行为。

`ready` 表示有依据认为当前粒度合适，`needs-split` 表示仍有多个可分别交付的部分。材料不足时保留缺口。无需拆分的需求保持原样，拆分判断本身不生成新的执行任务。

## 平级任务与前置依赖

需要拆分时，各 task 分别承接明确的需求范围。前置依赖说明某项工作需要先取得什么交付；集成、组合验证或整体验收也是普通 task，依赖所需能力的交付。

例如，两项能力可以分别实现，另一个 task 负责接通完整流程并验证组合行为。三项处于同一级，原需求继续提供共同的目标、范围和验收依据。各项的验收合起来应覆盖原需求，单项完成不自动证明整体完成。

拆分结果沿用项目约定的承载方式，每项能够被明确引用即可。文档组织方式由当前交接与追踪需要决定。

## 记录与后续执行

拆分判断保存在需求工作区的 `decomposition.md` 中，记录来源、判断依据、拆分结果引用和未解决问题。只请求评审时，拆分方案保留为建议；已有落实授权时，才写入结果并同步相关引用。

已有拆分时先核对并复用有效内容。来源变化后，重新判断受影响的范围、前置依赖和验收覆盖。无法确定记录位置时，返回未保存的草稿。

后续执行由调用方安排，目标、范围和验收已明确的工作交给 [execute-task](execute-task.md)。无需拆分、拆分已落实和功能已交付是不同结论。
