# architecture-steward：维护经过确认的架构决定

换一个实现者继续工作时，需要知道模块由谁负责、状态保存在哪里，以及哪些依赖可以建立。`architecture-steward` 把这些结构决定保存在 `ARCHITECTURE.md` 中，并维护它们的确认状态。

具体执行要求见 [SKILL.md](../skills/architecture-steward/SKILL.md)。

## 哪些内容值得成为架构决定

架构文档的价值在于帮助后续实现者作出一致的结构选择。一条内容应当表达当前要建立或改变的职责、状态归属、边界、依赖方向，或跨模块的数据与控制流。

例如，“导出服务负责管理导出任务状态，页面通过查询接口读取进度”包含职责与读取关系；“导出文件包含订单编号”表达业务要求，适合留在需求说明中。

候选决定可以来自讨论、Spec、实现或审查。AI 先判断其中哪些语义属于架构，再交给人确认，使架构文件保持聚焦，也减少确认时的阅读负担。

## 为什么确认到每个决定

同一段讨论可能包含几个可以独立改变的决定。把它们分开记录，就能只重新讨论实际变化的部分，保留其他已经确认的内容。

文字决定用 `[ ]` 表示待确认、`[x]` 表示已确认；每张架构图也有自己的确认状态。确认针对已经写出并展示的当前内容，让双方清楚接受的是哪一个版本的决定。

例如，模块职责保持不变，但状态读取方式需要调整，就只重新打开受影响的决定。单纯排版变化保留原状态。删除已确认决定时，也先把删除意图交给人确认。

## 让修改有明确入口

实现和审查可能发现现有架构需要改变。这时交回具体决定、缺口或候选变化，由 `architecture-steward` 整理并等待确认。后续实现据此获得新的明确依据。

文件位置由调用方明确指定，或在已明确需求 Spec 时使用其所在目录的默认候选。路径不清楚时先确定位置，避免把偶然读到的同名文件当成当前任务的架构依据。

## 与需求、规则和执行的关系

需求说明承载业务行为，Ticket 承载任务范围，[rule-steward](rule-steward.md) 管理可重复使用的项目规则。架构文件聚焦结构决定，相关材料可以各自保持清晰。

`architecture-steward` 完成的是决定的整理与确认。后续开发仍由调用方交给 [execute-task](execute-task.md) 等执行环节；当前任务已有明确依据时，可以直接继续相应工作。

整套流程见 [项目总览](overview.md)。
