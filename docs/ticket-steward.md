# ticket-steward：维护任务拆分与交付责任

任务拆出来之后，仍可能出现粒度过大、需求遗漏、重复工作或依赖错误。`ticket-steward` 检查已有 Ticket 的拆分质量，并把确认后的调整方案落实到票据和关系中。

具体执行要求见 [SKILL.md](../skills/ticket-steward/SKILL.md)。

## 用交付判断粒度

一项任务是否适合一次实现，取决于它能否形成聚焦、可独立验证的交付。文件数和代码行数很难表达这一点：一个完整行为可能跨多个模块，同一个文件也可能包含几个独立能力。

例如，单次导入与带重试、恢复机制的批量导入，可能各自具有独立的实现和验收价值。相反，同一次导入的正常输入、错误输入和边界情况，通常共同定义这一能力的完整行为。

`ready` 表示有依据认为当前粒度合适，`needs-split` 表示仍有多个可分别交付的部分。材料不足时保留缺口。粒度判断与执行许可、依赖是否满足、功能是否完成分别表达，方便调用方安排下一步。

## 分清工作承接与执行前置

父子关系说明一部分工作由谁承接，执行前置说明某项工作需要先取得什么交付。两种关系可以重叠，也可以跨越不同分支。

如果两个功能都需要同一份解析能力，可以根据已确认的关系共享这一任务，避免重复实现。各功能仍需检查自己的剩余责任，例如把解析结果接入业务流程、处理错误，以及完成整体验收。

这也是为什么子任务完成后，父任务仍可能有工作要做。

## 调整之后，原任务去哪里

拆分方案需要说明原任务还承担什么。如果仍有集成或组合验证，就保留父任务并明确剩余范围；如果所有工作都由新任务完整承接，就按确认的方案处理替代关系，让原任务退出待执行范围。

Matt 的 `to-tickets` 负责生成需要的新票，`ticket-steward` 接着维护原票、依赖、已有索引和拆分记录。仅有新票还不足以说明调整完成，相关引用与交付责任也需要一致。删除原票需要明确授权，并保留必要的来源与替代追溯。

## 记录与后续执行

拆分评审保存在需求工作区的 `decomposition.md` 中，记录来源、关系、粒度和未解决问题。只请求评审时，调整方案保留为建议；落实已确认方案时，才修改相应票据与关系。

来源变化后，可以沿受影响的任务重新判断。后续执行由调用方安排，明确的单个任务交给 [execute-task](execute-task.md)。拆分完成说明任务集合已整理一致，功能交付还需要实现与验证。

整套流程见 [项目总览](overview.md)。
