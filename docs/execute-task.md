# execute-task：组织一个明确任务的执行

任务的目标、范围和验收已经明确之后，还需要有人协调实现、审查、返修和结果交接。`execute-task` 承担这部分工作，让参与者围绕同一个任务推进，并在需要新决定时把问题交回调用方。

本文解释它的设计与使用边界；具体执行要求见 [SKILL.md](../skills/execute-task/SKILL.md)。

## 为什么需要执行编排

一次实现提交之后，仍有几件事需要判断：该由谁检查，审查意见是否属于本任务，修改后需要谁再看，以及当前是否已经可以结束。如果这些判断散落在多次临时交接中，就容易丢失原始要求、漏掉复查，或在修复过程中扩大范围。

`execute-task` 由协调者（Controller）统一处理这些交接。实现者（Implementer）负责业务代码修改；独立审查者提供问题与依据；调用方（Caller）提供任务，并接收最终结果或需要补充的决定。调用方可以是人，也可以是上游流程。

这使任务的推进有明确负责人，同时保留实现与审查各自的判断职责。

## 实现方法由实现者使用

任务编排关注参与者怎样协作，TDD、调试等方法关注具体工作怎样完成。本项目的组合方式在实现阶段使用 Superpowers 的 `test-driven-development`，应在任务交接时明确给实现者。

两者分开，使执行编排可以服务于不同类型的开发任务。实现者选择和使用方法时，仍以任务要求、项目约定和已有授权为依据；遇到未决定的产品行为，仍需交回调用方。

## 全量审查与返修分别解决什么

实现提交后，协调者围绕本任务的全部已提交变更，依次安排 [task-review](task-review.md) 和 [rules-review](rules-review.md)。前者检查需求与设计，后者检查项目规则；审查者从原始任务和明确的代码范围出发形成判断。

首次任务审查与规则审查由相互独立、不继承既有会话上下文的 agent 承担。必要依据通过明确交接提供，让审查者从任务和代码事实建立判断，减少此前讨论中的假设对结论的影响。

审查提出的问题由独立复审者判断是否成立、是否适用于原任务。复审者同样不继承既有会话上下文，接收原始任务、变更范围、问题与依据；再次提出的问题还会附此前处理理由及本轮异议。这样，审查意见到实际修改之间有一次明确的核对。需要修复时继续交给原实现者，保留它对实现的了解。

返修本身也会改变代码，可能引入新问题，因此已经参与审查的人还要检查本轮修改。沿用原审查者，便于结合此前疑点和处理结果判断新变化。例如，规则审查要求调整数据访问方式，修改也可能影响需求行为，所以此前通过的任务审查仍需参与复查。全量审查建立最初的判断，返修后的检查验证新变化。

## 哪些决定仍属于调用方

调用方负责提供当前任务的约束与来源。在本项目的组合方式中，采用架构管理协议时，这些上下文包含适用的 `ARCHITECTURE.md` 路径及已确认决定，以及必要的 ADR、Spec 来源。实现者和独立审查者由此获得共同依据，无需依赖上游会话记忆。交接前发现材料冲突时，由调用方组织澄清；执行中发现冲突或需要改变架构决定时，将具体问题交回调用方，需要变更的决定由 [architecture-steward](architecture-steward.md) 维护并交人确认。

问题是否成立、是否属于任务，以及修法是否获得授权，是三个不同的判断。前两个有了结论，仍可能需要调用方选择具体行为。

例如，任务要求“无法处理的输入必须报错”。实现改为拒绝这些输入后，独立复审确认它与当前公开接口的约定存在矛盾。增加支持和收窄公开接口会形成不同的使用约定。原任务没有决定这一点时，协调者会把选择交回调用方。

原始任务及必要上下文已经确定行为时，则可以在授权范围内继续返修。返回调用方主要用于补充决定性事实、解决任务或合同分叉，以及处理自动推进未能解决的问题。已有实现和审查结论会一并交接，方便继续。

问题处理过程中返回调用方，表示暂停自动推进、等待补充。补充内容没有改变原任务的目标、范围或验收时，继续原任务，复用已有参与者和判断上下文；这些条件发生变化时，则结束当前执行，由调用方重新发起任务。这个区分让已有工作可以接续，也让新的任务边界得到明确交接。

## 它在开发流程中的位置

上游负责明确任务，必要时通过 Spec 和 Ticket 传递范围、验收和上下文；`execute-task` 负责这一个任务的执行闭环。两项审查都没有已确认问题和无法判断项之后，它返回实现、验证、审查结果及剩余风险。

后续合并、多个任务的集成和整体验收由调用方继续安排。需要重新决定需求、架构或规则时，也由相应环节处理，再提供清楚的任务依据。

整套流程见 [项目总览](overview.md)。
