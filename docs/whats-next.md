# whats-next：判断下一步由谁继续

开发中停下来，有时是因为不知道当前问题属于哪一层：继续实现、补充需求、修正 Spec，还是调整架构和规则。`whats-next` 判断这一步的责任归属，给出依据和建议，然后停止。

具体执行要求见 [SKILL.md](../skills/whats-next/SKILL.md)。

## 按需要解决的问题选择入口

判断下一步，要看当前需要推进或修正什么。问题在哪个阶段被发现，并不决定它由谁处理。

| 当前事实 | 下一步的方向 |
| --- | --- |
| 已有任务的粒度、执行顺序或覆盖关系有问题。 | 交给 [task-steward](task-steward.md) 评审和维护任务拆分。 |
| 预期行为已经明确，代码没有正确实现。 | 明确修复范围与验收后，交给执行环节。 |
| 两种产品行为都可接受，还没有作出选择。 | 回到需求或契约讨论。 |
| 决定已经明确，但 Spec 表达错误。 | 修正 Spec。 |
| 当前需要读取或改变已确认的架构决定。 | 交给架构维护环节。 |
| 规则定义本身有问题。 | 交给规则维护环节。 |

判断依赖某份现有材料时，可以先只读核对它。这样，已经作出的决定不会仅因暂时缺少上下文就被重新打开。

## 为什么只给一个归属并停止

一次输出聚焦当前最需要处理的责任，方便调用方明确交接。后续可能还有其他工作，但当前缺口应先由合适的环节解决。

判断归属与实际修改分开，可以避免路由过程中顺手改写需求、规则或代码。`whats-next` 提供方向，接下来由你或调用方安排对应工作，并保留该环节原有的权限与确认要求。

## 什么时候用其他 skill

任务已经明确且可以执行时，直接使用 [execute-task](execute-task.md)。需要管理架构或规则时，分别使用 [architecture-steward](architecture-steward.md) 和 [rule-steward](rule-steward.md)。

如果疑问是当前方案是否值得继续，[way-out](way-out.md) 会比较不同方向；`whats-next` 则聚焦谁应该接手当前问题。保存讨论供以后继续时，用 [checkpoint](checkpoint.md)。

整套流程见 [项目总览](overview.md)。
