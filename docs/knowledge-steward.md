# knowledge-steward：项目知识维护

`knowledge-steward` 维护项目中值得长期依赖的知识，使有效内容准确、可找到、可追溯。维护范围可以是一个主题、一批相关资料或已有知识库。

长期知识承接材料中当前有效、后续仍需使用的含义。Spec、研究笔记和项目文档可以承载这些知识；探索、执行和验收材料可以提供整理依据。工作仍在进行或长期组织方式尚未确定时，先维护现有材料。

具体执行要求见 [SKILL.md](../skills/knowledge-steward/SKILL.md)。

## 从具体管理问题出发

根据用户意图、现有材料和实际使用需要判断要处理什么，再选择维护动作：

| 当前情况 | 可能的处理 |
| --- | --- |
| 已确认的需求变化还未反映在 Spec 中 | 在授权内更新受影响内容，关联确认依据。 |
| 研究结论、原型验证与已采纳方案混在一起 | 理清确认状态和适用条件，保留各自证据与未决问题。 |
| 资料重复、引用失效或难以找到当前依据 | 维护现有目录、索引和引用，厘清材料之间的关系。 |
| 旧任务或实验材料中哪些内容值得沉淀存在疑问 | 确定仍需使用的知识和合适载体，需要提交时整理候选范围与承接工作。 |
| 现有知识与引用已经满足需要 | 说明依据，维持现状并结束本轮维护。 |

例如，可以在探索尚未结束时使用：

```text
使用 knowledge-steward 维护支付重试相关资料。
研究笔记已经更新，决定地图还引用旧结论，部分原型记录仍被后续任务使用。
请修正有依据的内容和引用，明确当前可用的知识入口。
```

补充内容先明确需要回答的具体使用问题及其依据，再沿现有材料和引用核对缺口。需要新增文档或索引时，位置按项目约定或本轮安排确定。本轮管理问题不依赖新的组织方案时，沿用现有材料即可完成维护。

## 保持各环节的职责

探索、研究、原型、需求准备、实现和审查会形成不同性质的知识与证据。`knowledge-steward` 管理这些内容及其材料关系；需要新调查、新决定、实现修复或重新审查时，交给相应环节。具体说明见 [工作流材料职责](../skills/knowledge-steward/references/workflow-materials.md)。

普通材料的内容与引用更正按已有授权处理。领域模型、架构、规则和任务等有专门维护约定时，变更遵循对应入口的协议。已有有效内容可以直接读取和引用。

例如，探索期间由 Wayfinder 地图维护索引，具体决定在票据或评论中；完成后将有效决定承接到对应知识载体。`checkpoint` 的快照支持未结束讨论的接续；执行和审查交接提供其范围内的事实与发现。

## 保留依据与适用范围

功能约定沿用已确认需求和变更。判断功能是否完成时，依据已有交付记录或用户对实际交付结果的确认；判断行为是否已被验证时，依据具体的验证结果及其覆盖范围。研究、排障和原型结论可以独立保留，生产方案是否采纳另看相应决定。结论保留影响适用范围的条件与限制；材料存在无法裁决的冲突时，继续处理不受影响的部分，并返回具体未决事项。

按材料用途选择写入内容：功能说明承载后续使用和维护所需的范围、行为、约束与理由；本次工作的执行状态、验收结果和验证覆盖用于本轮处理结论。研究笔记、历史决定和实验记录按其使用需要保留依据与原始事实，通过更正或替代引用关联后续变化。业务要求、外部契约与本项目的实现选择分别表达，便于后续使用者判断适用范围。

## 提炼长期知识与准备提交

先判断后续需要回答什么问题，再将材料中仍需使用的含义表达为当前约束、决定、行为、必要理由或有条件的研究结论。表达保持来源的确认状态、适用条件和约束强度。以缺少理由是否会妨碍理解当前关键决定或作出具体后续判断，决定是否承接该理由；当前约束或决定已能回答使用问题时，直接表达约束或决定。例如，已确认的 MySQL 5.7 兼容要求可以作为长期约束；仍需使用的实验结论若来自 MySQL 5.7 环境，则保留这一实验条件。

按项目已有职责和实际用途选择承载位置，使当前知识直接可用，展开的决定依据和原始证据按需可查；需要 Git 建议时明确提交候选。代码、类型和测试已经准确表达的实现事实可继续引用；业务行为、关键决定及理由、适用条件按职责进入相应文档。功能完成后，仍作为后续知识载体使用的 Spec 按已确认的最终范围整理；文件名和目录本身不能证明其值得长期保留。

Wayfinder 地图与决定票、to-tickets 拆分与实施票服务探索和执行，完成后由合适的知识载体承接有效内容与引用。执行记录、接口核对和验收报告为知识维护提供事实依据，其独立记录价值按实际用途判断。有明确的审计、复盘或原始记录访问要求时，沿用满足该用途的记录。

例如，功能完成后，Spec 仍引用一张记录最终行为的决定票。收尾时把缺失的行为补入 Spec，架构继续引用 Architecture，接口事实引用已有代码；处理引用后，决定票无需首次纳入 Git。票据的讨论经过、实现 SHA 和测试通过记录不必搬入 Spec。

尚未完成知识承接或引用迁移时，说明具体缺口、承接位置和收尾动作。进行中的任务、未决问题及真实下游所需的合同和实验数据继续使用原有材料；能持续回答使用问题的研究笔记也可以直接作为知识载体。

Git 建议结合知识承载关系、项目约定、跟踪与修改状态及访问需要，区分可直接提交、整理后提交、无需首次纳入的材料，以及已跟踪材料需要同步的更新。提交候选只确定纳入 Git 的范围；材料的内容维护、归档、删除和 Git 写操作分别按本轮已有授权执行，任务状态由任务维护流程处理。

判断任务以结论、依据和具体缺口清楚为完成标准；维护任务在已确定的范围内核对内容与依据一致，提炼后的确认状态、适用条件和约束强度保持原义，必要知识有合适载体，并检查本轮改动影响的入口与引用。需要提交建议时，说明候选范围及待整理事项。完成时说明本轮结论、实际改动和仍需承接的事项，过程材料继续留在本地不影响知识维护完成。

尚未结束的讨论可以使用 [checkpoint](checkpoint.md) 接续；整个开发流程见 [项目总览](overview.md)。
