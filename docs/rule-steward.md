# rule-steward：维护可重复使用的项目规则

项目中的一些约定需要被不同任务和审查者反复使用。`rule-steward` 管理这些规则的定义、编号、获取和退役，让使用者能找到当前有效的要求，并引用具体依据。

具体执行要求见 [SKILL.md](../skills/rule-steward/SKILL.md)。

## 让规则值得长期保留

每增加一条规则，后续任务就增加一份阅读、判断和维护成本。因此，候选规则需要有正确性依据，也需要证据说明它解决了值得反复防范的问题。

适合保留的规则通常对应 AI 容易忽略的长期约定，能够指导明确动作，并能通过具体事实判断是否遵守。一次性任务要求留在任务中，已经由现有规则覆盖的内容优先合并或调整。

规则还需要有清楚的生效条件和单独可判断的要求。这样，审查者才知道何时检查，以及问题究竟出在哪里。

## 让引用和获取保持可靠

规则保存在 `.agents/rules/` 中，按登记的分类组织，并使用稳定编号。编号让审查意见可以指向具体规则；目录用于发现完整的有效规则集合，正文承载完整要求和例外。

查询工具负责检查编号、文件路由和必要字段，返回当前规则或指定提交中的规则。目录和正文使用同一来源，使消费者能够围绕一致的规则版本作判断。

退役时保留历史编号、原因和替代信息。这样，旧引用仍能解释，同时后续审查可以区分当前要求与已经退出使用的规则。

## 分开验证结构、内容和行为

规则能被工具读出来，只说明格式与来源关系可以解析。它是否正确、值得加入，以及是否真的改善 AI 行为，需要其他证据。

| 验证 | 主要回答的问题 |
| --- | --- |
| 内容审查 | 要求是否有依据、适合长期使用，适用条件与义务是否清楚。 |
| 行为验证 | 实际消费者使用候选规则后，是否产生预期改善，且没有在相近但不适用的场景中过度触发。 |
| 结构验证 | 编号、登记、获取和退役状态是否一致。 |

新增规则和实质语义修改等维护，需要用精确候选文本进行隔离对照。规则退役并由其他规则替代时，则需要验证仍然有效的行为被保留。只读分析和格式检查各有用途，不能单独证明行为效果。

行为验证的结果会影响能否写入。验证失败，说明候选无效或越界，不能通过接受风险继续写入；无法验证则表示缺少有效、可比的行为证据，默认暂停写入。只有在本次维护中明确说明缺失证据、原因和剩余风险，并由你明确接受这些风险后，无法验证的候选才可能继续处理。一般性的“继续”或对修改方案的确认，不等于接受这项风险，也不会把未验证的结果变成验证通过。

## 与规则审查的分工

[rules-review](rules-review.md) 使用当前有效规则检查指定代码；`rule-steward` 处理规则自身是否需要新增、修改或退役。这样，审查中发现的代码问题和规则定义问题可以分别交给对应环节。

规则级别表达约束强度及处置要求，是否违反仍依据规则正文和事实判断。消费者需要保留这些区别，再由相应执行流程处理问题。

只有在明确的初始化或维护请求下，才建立或改变项目规则。需要审视规则对 AI 的授权、判断空间和证据要求时，可以使用 [bounded-agency-review](bounded-agency-review.md)。

整套流程见 [项目总览](overview.md)。
